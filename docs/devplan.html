NewBee OS 30 天开发计划

目标只有一句：30 天后，你用它而不是 Wise Agent 管一笔真实交易。计划按"先跑通一条竖切、再加宽"的顺序排，每一天都有交付物和完成标准；工具、账号、数据库、引擎函数、仓库约定、变更协议、砍单顺序全部写死，开发中改需求时照第 8 节的规则改。

00结论与策略

一个月能用，前提是"能用"定义清楚、顺序不乱、砍单果断。

  1. "能用"的定义（Day 30 验收）：新建交易 → 上传合同 → AI 抽取 → 你确认 → 自动生成关键日期和任务 → Today 页每天告诉你该干什么 → 关键日期出现在 Google 日历并有提醒 → 联系人和房子挂在交易上 → 你的 5 套 Playbook 全部在里面 → 进行中的交易全部迁进来。不包括：客户 App、Deal Health、Net Sheet、短信收件箱、营销、报表。
  2. 先架构还是先 flow？两个都对，但各只做一半。架构只做"改起来最贵"的骨架：monorepo、6 张核心表、Auth、core 包的函数签名——Day 1–2 做完。然后立刻做 flow：Week 1 用最丑的界面把"合同 → 抽取 → 日期 → 任务 → Today"整条线跑通（竖切 / walking skeleton）。跑通之后再加宽（更多字段、更多表、更多页面）。不要先把 20 张表全建完再写第一个页面，那样第 3 周才能看到东西，而且表一定会改。
  3. 时间假设：工作日每天 2–3 小时 + 周末各半天 ≈ 每周 20 小时，四周 80 小时。用 Claude Code 写代码，你的角色是产品经理 + 测试员：每天定目标、给上下文、跑一遍、提 bug。计划按这个强度排；如果一周不到 15 小时，按第 9 节砍。
  4. 三条铁律：① 业务逻辑只写在 packages/core，UI 永远是薄的；② 数据库改动一律走 migration，不手改；③ 每天结束时 main 分支必须能跑、能部署。
  5. Week 1 结束就要用真合同测试（脱敏后的），不要等到 Week 4。抽取准确率是整个产品的地基，越早发现问题越便宜。

约定（写进 CLAUDE.md）

  • 命名：表 snake_case 复数；TS camelCase；Key-Value 的 key 用规格第 2 节的英文 key，永不改名（改名 = 新 key + 迁移）
  • 时间：数据库全部 timestamptz 存 UTC；日期型字段（closing_date）用 date；所有"第 N 天"计算在 core 里做，UI 不算
  • 金额：numeric(12,2)，UI 显示才格式化
  • 每个表都有 id uuid、agent_id、created_at、updated_at、deleted_at（软删）
  • Migration 只增不改；改字段 = 加新字段 + 回填 + 旧字段标 deprecated
  • 每次 migration 后跑 supabase gen types 更新 core 类型
  • core 不许 import 任何 UI 或 Supabase client；只吃纯数据、吐纯数据

分支与部署

  • 单人开发：直接在 main 上小步提交；一天一个可运行版本
  • 大改动（换表结构、换抽取 schema）开分支，Vercel 自动给预览链接，手机上测完再合
  • Vercel：main → 生产域名；分支 → 预览域名
  • Supabase：migration 通过 CLI supabase db push 推到 dev；Week 4 起 prod 只在你手动确认后推
  • Secrets：Vercel 环境变量 + Supabase Function secrets；本机 .env.local；仓库里永远没有 key

Week 1 六张核心表的 DDL（直接作为 0001_init.sql）

create type deal_type as enum ('seller','buyer','lease_listing','lease_tenant','property_mgmt');
create type deal_stage as enum ('lead','pre','active','offer','under_contract','closing','closed','terminated');
create type doc_status as enum ('uploaded','extracting','review','confirmed','failed');
create type ms_status as enum ('pending','done','overdue','na');

create table agents (
  id uuid primary key references auth.users(id) on delete cascade,
  name text not null, brokerage text, timezone text not null default 'America/Chicago',
  settings jsonb not null default '{}', created_at timestamptz default now()
);

create table deals (
  id uuid primary key default gen_random_uuid(),
  agent_id uuid not null references agents(id),
  type deal_type not null, stage deal_stage not null default 'lead',
  title text not null, property_id uuid, primary_contact_id uuid,
  playbook_id uuid, playbook_version int,
  pinned boolean default false, closed_at date, terminated_at date,
  created_at timestamptz default now(), updated_at timestamptz default now(), deleted_at timestamptz
);

create table documents (
  id uuid primary key default gen_random_uuid(),
  deal_id uuid not null references deals(id) on delete cascade,
  agent_id uuid not null references agents(id),
  storage_path text not null, doc_type text, page_count int,
  status doc_status not null default 'uploaded', extraction jsonb, error text,
  uploaded_at timestamptz default now(), confirmed_at timestamptz
);

create table deal_fields (
  id uuid primary key default gen_random_uuid(),
  deal_id uuid not null references deals(id) on delete cascade,
  key text not null, value_text text, value_num numeric(14,2), value_date date,
  source_doc_id uuid references documents(id), source_page int, source_quote text,
  confidence numeric(4,3), confirmed_at timestamptz, confirmed_by uuid,
  version int not null default 1, superseded_at timestamptz,
  created_at timestamptz default now()
);
create index on deal_fields (deal_id, key) where superseded_at is null;

create table milestones (
  id uuid primary key default gen_random_uuid(),
  deal_id uuid not null references deals(id) on delete cascade,
  key text not null, label text not null, due_at timestamptz,
  derived_from jsonb, status ms_status not null default 'pending',
  manual_override boolean default false, client_visible boolean default true,
  calendar_event_id text, created_at timestamptz default now(), updated_at timestamptz default now(),
  unique (deal_id, key)
);

create table tasks (
  id uuid primary key default gen_random_uuid(),
  agent_id uuid not null references agents(id),
  deal_id uuid references deals(id) on delete cascade,
  title text not null, stage text, due_date date,
  anchor_milestone_key text, offset_days int, playbook_rule_id text,
  assignee uuid, priority int default 0, done_at timestamptz,
  client_visible boolean default false, created_at timestamptz default now(), updated_at timestamptz default now()
);
create index on tasks (agent_id, due_date) where done_at is null;

-- RLS：第 1 个月一条规则走天下
alter table deals enable row level security;  -- 其余表同理
create policy "own rows" on deals for all using (agent_id = auth.uid()) with check (agent_id = auth.uid());
为什么 deal_fields 用"版本行"而不是 jsonb：你要的"价格变化历史、amendment 覆盖了什么、每个值来自哪份文件第几页"都靠这张表；jsonb 一改就丢历史。查询"当前值"就一句 where superseded_at is null。

05core 引擎：函数签名先定死

这些签名 Day 2 就写进 packages/core，先用 throw new Error('todo') 占位，UI 和引擎并行开发都不会互相卡住。

// engines/dates.ts —— Texas 常规：天数按日历天；落在周末/联邦假日时是否顺延由规则决定
export type DateRule = { anchor: string; offset: number; unit: 'calendar'|'business'; rollForward?: boolean; time?: '17:00' };
export function addDays(base: Date, rule: DateRule, holidays: Date[]): Date;

// engines/milestones.ts —— 从当前字段算出全部里程碑；任一锚点变了整表重算
export type Field = { key: string; value: string|number|Date|null };
export function computeMilestones(fields: Field[], rules: MilestoneRule[], holidays: Date[]): Milestone[];
export function diffMilestones(before: Milestone[], after: Milestone[]): { changed: Milestone[]; added: Milestone[]; removed: string[] };

// engines/playbook.ts —— Playbook 定义 + 里程碑 → 任务；已完成的任务不重建，只更新到期日
export function instantiate(playbook: Playbook, milestones: Milestone[], enabledAddenda: string[]): TaskDraft[];
export function reconcile(existing: Task[], drafts: TaskDraft[]): { create: TaskDraft[]; update: Partial<Task>[]; keep: Task[] };

// engines/commission.ts
export function commission(input: { price: number; pct: number; brokerFeeTable: FeeTable; referralPct?: number }): { gci: number; fees: Fee[]; nci: number };

// ai/extract.ts —— 只在服务端调用；返回 zod 校验过的结果，字段带来源与置信度
export type Extracted = { key: string; value: string; page: number; quote: string; confidence: number };
export function extractContract(pdf: Uint8Array, docTypeHint?: string): Promise<{ docType: string; addenda: string[]; fields: Extracted[]; pages: number }>;
export function needsReview(f: Extracted): boolean;   // 数值/日期字段 或 confidence < 0.9 → true

// ai/classify.ts
export function classifyDocument(firstPagesText: string): Promise<'trec_1_4'|'amendment'|'financing_addendum'|'hoa_addendum'|'lease'|'inspection'|'other'>;

必须有的测试（Vitest，Week 1 就写）

  • dates：Effective 9/1 + 10 天 = 9/11；落周日是否顺延到周一；跨年；美国联邦假日表
  • milestones：给一组字段，断言 11 个里程碑的日期；改 closing_date 只有 closing 相关的变
  • playbook：Seller 模板实例化出 N 条任务；无 HOA addendum 时不生成 HOA 任务；reconcile 不会重建已完成任务
  • extract：5 份脱敏合同做"黄金集"，断言关键字段全对（跑一次要花钱，手动触发不进 CI）

抽取的服务端流程（Edge Function extract-contract）

  • 触发：documents 插入一行 → Database Webhook → Function
  • 下载 PDF → classifyDocument（Haiku，只看前 2 页）→ extractContract（Sonnet，整份 PDF）
  • 结果存 documents.extraction，状态 → review
  • 每个字段插 deal_fields（confirmed_at 空）；needsReview 为 false 的自动 confirm
  • 你在确认页点"全部确认并派生" → 调 computeMilestones + instantiate + reconcile → 写 milestones / tasks → 写 activities → 触发日历同步
  • 失败：状态 failed + error，UI 提示重传；绝不静默

08变更协议：开发中改需求怎么改才不返工

你想改的东西正确做法禁止
加 / 改数据库字段新 migration 加字段 → gen types → core 类型跟着变 → UI 最后改；旧字段留着标 deprecated，两周后再删手改 Supabase 表；改旧 migration 文件
抽取字段增删改附录 C 的 schema（加 key 不改旧 key）→ 黄金集跑一遍 → 提交 prompt 新版本号（prompts/extract-contract.v3.md）改已有 key 的名字或语义
Playbook 任务 / 天数改 JSON → 导入为新版本 → 只对新交易生效；要应用到进行中交易，用"重新实例化"按钮（reconcile 保留已完成）直接改 tasks 表里的到期日当作改模板
日期规则（顺延、假日）改 dates.ts + 先加测试用例；全部交易重算并把变化写进 activities在 UI 里 hardcode 天数
阶段定义enum 只加不删；旧值映射到新值的 migration删 enum 值
页面布局、文案、颜色随便改，不用记录—
新模块（如 Net Sheet）先在 core 写引擎 + 测试，再建表，最后 UI；先写一页 ADR 说明范围从 UI 开始做
推翻架构决策写 ADR（为什么、代价、迁移路径），过一夜再决定当天冲动重构
不返工的秘诀只有一个：数据和规则（core + migrations）是慢变层，界面是快变层。所有"不断修改"都尽量落在快变层；一旦要动慢变层，就按上表走版本，不覆盖。

# NewBee OS

## 这是什么
一个人的房地产交易操作系统（self-use first）。核心思想：合同即数据——上传合同 → AI 抽取 Key-Value → 确认 → 派生里程碑 / 任务 / 日历 / 提醒 / 佣金。
产品规格见 docs/spec.html，30 天计划见 docs/devplan.html，每日日志见 docs/log.md。开工前先读 log.md 最后 3 条。

## 技术栈（不要换、不要加计划外的库）
pnpm monorepo · TypeScript · Next.js App Router + Tailwind + shadcn/ui · Supabase (Postgres/Auth/Storage/Edge Functions) · Vitest · Anthropic SDK · zod · dnd-kit · date-fns-tz

## 目录
packages/core = 纯业务逻辑（types / schemas / engines / ai / playbooks / test），禁止 import UI 或 supabase client
apps/web = Next.js；只做界面和调用；不写业务规则
supabase/migrations = 只增不改；每次改动后运行 `pnpm gen:types`

## 约定
- 表 snake_case 复数；TS camelCase；Key-Value 的 key 永不改名
- 所有表：id uuid, agent_id, created_at, updated_at, deleted_at(软删)
- 时间 timestamptz(UTC)；日期 date；金额 numeric(12,2)
- 业务日期计算只在 packages/core/engines/dates.ts
- AI 只在服务端调用（Route Handler / Edge Function）；用 tool_use 强制 JSON；system prompt 加 cache_control
- 数值/日期字段或 confidence < 0.9 的抽取结果必须进待确认，不得自动派生
- 失败必须落 status=failed + error，禁止静默

C附录 C · 抽取 Prompt 骨架（system，缓存）

你是德州住宅房地产交易的合同数据抽取器。输入是一份 PDF（TREC 合同、addendum、amendment、租约或检查报告）。
只输出 tool 调用 save_extraction，不要解释。

规则：
1. 逐字段给出 value、page（从 1 起）、quote（原文 ≤ 120 字符）、confidence（0–1）。找不到就不要输出该字段。
2. 日期统一 YYYY-MM-DD；金额只留数字；天数为整数；勾选项用 true/false。
3. 识别文档类型 docType，以及合同第 22 段勾选的 addenda 列表。
4. 手写内容看不清时给低 confidence，不要猜。
5. 多轮 counter / amendment：只抽最终生效的值，并在 notes 里说明依据。

字段（key · 含义 · 通常位置）：
effective_date · 合同生效日 · 末页 "Effective Date"
sales_price · 3C 总价 · ¶3
cash_portion · 3A 现金部分 · ¶3
loan_amount · 3B 贷款额 · ¶3
earnest_money · 诚意金 · ¶5
earnest_money_due_days · 诚意金交付天数 · ¶5
option_fee · Option 费 · ¶5
option_period_days · Option 期天数 · ¶5
